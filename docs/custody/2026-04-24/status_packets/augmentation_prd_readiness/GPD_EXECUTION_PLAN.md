# ZPE-Ink GPD Execution Plan

## Phase Name / Number Or Proposed Phase Name

Proposed inserted phase: `05.1 Interoperability Truth Reconciliation And Augmentation Readiness`

Reasoning:

- The active `.gpd` project is real and complete through Phase 05.
- The roadmap should not be rewritten in this planning pass.
- The next wave is a bounded follow-on that sits immediately after Phase 05 and before any true new commercialization or runtime branch.

This phase should remain proposed until the user authorizes roadmap-level installation.

## Dependency Chain

1. archived Phase 05 `NO-GO` packet
2. repo-truth reconciliation
3. local CPU rerun manifest
4. follow-on decision artifact
5. conditional augmentation branch design

Nothing in the augmentation branch is allowed to start before steps 1-4 are complete.

## Wave Plan

### Wave 1: Truth Surface

- build repo truth matrix
- classify contradictions
- define governance-compliant later-change queue

### Wave 2: Local CPU Proof Refresh

- rerun tests, parity, contracts, build, install smoke
- classify blockers precisely

### Wave 3: Follow-On Decision

- decide closure vs branch vs bounded reopen
- preserve archived `NO-GO` unless superseded by explicit artifact

### Wave 4: Conditional Augmentation Design

Only if Wave 3 reopens the lane:

- design integer-canvas, binary-codebook, or hybrid candidate path
- define corpus, HF, and possible RunPod needs
- write candidate branch contract

### Wave 5: Conditional Augmentation Execution

Only if Wave 4 is approved:

- implement the candidate branch
- produce bounded proof and benchmark artifacts
- preserve `.zpink` authority and fresh rerun gates

### Wave 6: Conditional Final Verification

Only if Wave 5 completes:

- verify candidate value against the reopened lane
- decide branch-only, bounded milestone, or kill

## Subagent Plan

- Repo-truth/governance agent:
  builds contradiction matrix and governance queue.
- Proof/validation agent:
  refreshes local CPU proof packet and classifies blockers.
- Verification agent:
  synthesizes follow-on decision packet and readiness boundary.
- Custody agent:
  maintains HF custody for large proof and future large corpora.
- Candidate augmentation design agent:
  drafts branch contract only if the lane is reopened.

The lead planner/verifier retains final authority on the lane decision.

## Verification Loop

1. Compare live repo surfaces against archived authority artifacts.
2. Refresh the local CPU evidence packet.
3. Re-evaluate the lane against the sovereign acceptance gate.
4. If the result is still closure, stop.
5. If the result is branch/reopen, validate that the candidate augmentation remains narrower than the evidence.

## Checkpoint Policy

- Checkpoint after Wave 1 if contradictions are worse than expected or require human policy judgment.
- Checkpoint after Wave 2 with the rerun manifest.
- Mandatory checkpoint before any roadmap insertion or candidate implementation.
- Mandatory checkpoint before any RunPod escalation.
- Mandatory checkpoint before promoting any candidate branch into repo-front-door language.

## What Must Be True Before `gpd-execute-phase` Starts

- A proposed `05.1` phase is accepted by the user or converted into an approved branch-only execution packet.
- Truth matrix exists and is coherent.
- Local CPU rerun manifest exists and clearly classifies all major gates.
- HF requirements for any large upcoming artifacts are defined.
- RunPod requirement is either `not needed` or named precisely.
- GitHub-required-later surfaces are listed but not conflated with HF custody.
- Candidate augmentation scope is written as candidate-only and does not overwrite the sovereign `.zpink` authority surface.
